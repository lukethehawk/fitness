===============================================================================
CONTESTO GENERALE
===============================================================================

Il progetto nasce come webapp semplice per seguire una scheda palestra personale,
ma e stato progressivamente reso piu generico e personalizzabile.

La direzione scelta e stata:

- niente account;
- niente backend obbligatorio;
- nessun dato inviato a server dell'app;
- uso diretto da browser o come PWA;
- massima personalizzazione della scheda;
- export semplice verso app esterne come Joplin, note, email, cloud o Excel;
- beta separata per testare funzioni piu delicate senza rompere la pubblica.

La scelta tecnica principale e stata mantenere una webapp statica.
Questo riduce complessita, costi e barriere per utenti non tecnici.

DEPLOY / GITHUB PAGES
===============================================================================

- Il progetto e una webapp statica.
- Se non serve una build, la modalita piu semplice e consigliata e GitHub Pages
  con:
  Source: Deploy from a branch
  Branch: main
  Folder: /root
- Questa modalita evita workflow GitHub Actions non necessari.
- Se si usa GitHub Actions per Pages, il workflow deve avere permessi corretti:
  contents: read
  pages: write
  id-token: write
- L'errore "Requires authentication" o status 401 in actions/deploy-pages indica
  un problema di permessi/autenticazione del workflow, non un errore del codice
  JavaScript.
- I run Actions gia creati possono restare nello storico anche dopo aver
  eliminato o disattivato un workflow.
- Prima di nuove modifiche, definire quale metodo di deploy viene usato
  ufficialmente.

VERSIONE STABILE - STATO FUNZIONALE
===============================================================================

Obiettivo:

- fornire una scheda palestra personalizzabile e condivisibile, utilizzabile da
  tutti senza login e senza configurazioni tecniche.

Caratteristiche principali:

1. Scheda personalizzabile

- La scheda non e piu vincolata a tre giorni fissi.
- L'utente puo avere da 1 a 7 giorni di allenamento.
- Ogni giorno puo essere rinominato.
- Ogni giorno puo essere assegnato a un giorno della settimana.
- Gli esercizi preconfigurati possono essere eliminati.
- La scheda puo quindi essere ricostruita da zero.

2. Modalita modifica compatta

- In modalita modifica l'interfaccia diventa piu snella.
- Ogni esercizio mostra nome, numero serie, pulsanti +/- e azioni essenziali.
- Il drag and drop e pensato per essere piu usabile su iPhone.
- Le card alte della modalita normale non vengono usate per il riordino.

3. Catalogo esercizi

- Il catalogo usa free-exercise-db.
- Sono disponibili filtri per muscolo e attrezzatura.
- Ogni esercizio puo mostrare immagini animate.
- Sono previste piu varianti per gruppo muscolare.
- L'utente puo scegliere nomi in italiano o inglese.
- Ogni esercizio puo essere rinominato manualmente.

4. Lingua esercizi

- E stato aggiunto un toggle lingua nei settaggi.
- Italiano e inglese possono essere alternati.
- La rinomina manuale permette di correggere nomi poco naturali.

5. Timer

- Il timer e stato trasformato in bolla compatta.
- Di default e impostato a 60 secondi.
- I pulsanti 60/90/120/180 selezionano la durata.
- Il timer parte solo con Avvia.
- In modalita iOS shortcut, Stop viene nascosto per evitare confusione.
- Alla scadenza il pulsante non rilancia il timer per errore.

6. Timer iOS tramite Comandi Rapidi

- Su iPhone, la PWA o la pagina Safari puo essere sospesa in background.
- Per questo il timer JavaScript non garantisce notifiche affidabili.
- E stata aggiunta una modalita opzionale:
  shortcuts://run-shortcut?name=NOME_COMANDO&input=text&text=SECONDI
- L'utente configura un comando rapido chiamato, ad esempio, Timer Palestra.
- La webapp passa la durata selezionata.
- Il timer nativo iOS gestisce l'avviso a schermo bloccato.

7. Export Markdown

- Export giornata.
- Export settimana.
- File nominato con data italiana.
- Contiene:
  - nome allenamento;
  - esercizi svolti;
  - immagini associate;
  - peso;
  - serie completate;
  - note;
  - esercizi saltati.
- Gli esercizi saltati vengono evidenziati meglio.
- Il pulsante e stato rinominato in Esporta o condividi / Condividi, senza
  legarlo solo a Joplin.

8. Export Excel

- Export in formato .xlsx.
- Pensato per analisi, filtri e ordinamenti.
- Le immagini non vengono incluse.
- Ogni esercizio occupa una riga.
- Campi utili:
  - data;
  - giorno allenamento;
  - nome allenamento;
  - esercizio;
  - parte del corpo;
  - programma;
  - serie previste;
  - serie completate;
  - peso;
  - note;
  - stato.

9. Aggiornamenti e changelog

- Versione visibile in basso.
- Pulsante Novita con changelog leggibile.
- Controllo aggiornamenti.
- Pulsante Aggiorna che sostituisce la cache senza cancellare localStorage.
- Versione spostata in basso nella UI mobile per non coprire l'interfaccia.

10. Privacy

- Nessun account.
- Nessun server dell'app.
- Dati salvati nel browser.
- API key WorkoutX, se usata, resta locale.
- Export e backup sono responsabilita dell'utente.

===============================================================================
SCELTE TECNICHE IMPORTANTI
===============================================================================

1. App statica

- Pro:
  - semplice da pubblicare;
  - nessun costo server;
  - facile da usare;
  - buona per open source;
  - non richiede login.
- Contro:
  - niente sincronizzazione automatica;
  - storico legato al dispositivo/browser;
  - localStorage puo essere cancellato.

2. localStorage

- Usato per impostazioni, schede, progressi e storico beta.
- Sufficiente per una webapp semplice.
- Richiede backup/import per cambio dispositivo.

3. free-exercise-db

- Usato per catalogo e immagini esercizi.
- Permette di evitare richieste continue a servizi a pagamento.
- La qualita dei nomi italiani puo richiedere correzione manuale.

4. WorkoutX API

- Supportata come opzione.
- La chiave API viene salvata solo localmente.
- Non e inclusa nei backup.
- Dopo l'adozione di free-exercise-db e diventata meno centrale.

5. Timer iOS

- Non e possibile garantire notifiche affidabili solo con JavaScript su iPhone.
- La soluzione scelta e un bridge opzionale verso Comandi Rapidi.
- L'utente usa il timer nativo iOS, piu affidabile a schermo bloccato.

6. Export invece di sincronizzazione

- Export Markdown ed Excel permettono di portare i dati fuori dall'app.
- Backup/import aiuta cambio telefono o PC.
- Il self-hosting con SQLite resta idea futura, non prioritaria.

===============================================================================
PROBLEMI NOTI / NOTE APERTE
===============================================================================

1. Nessuna sincronizzazione automatica.
   I dati restano nel browser. Per cambio dispositivo usare backup/import oppure
   export.

2. localStorage non e un database.
   Va bene per uso semplice, ma non e ideale per storico molto lungo o multi-device.

3. Self-hosting rimandato.
   L'idea di una versione con SQLite/server esterno e interessante, ma per ora
   viene dopo soluzioni semplici come backup, export e storico locale.

4. iOS sospende JavaScript.
   Le notifiche del timer interno non possono essere affidabili a schermo
   bloccato. Il workaround consigliato resta Comandi Rapidi.

5. Traduzioni esercizi.
   Alcune traduzioni automatiche non sono perfette. Per questo esiste toggle
   lingua e rinomina manuale.

6. Beta non ancora stabile.
   Lo storico e i grafici sono in prova. Prima di portarli in produzione servono
   test reali.

7. Backup/import da mantenere aggiornato.
   Ogni nuova funzione che salva dati deve essere inclusa nel backup se serve al
   ripristino.

8. Problema aperto - Aggiunta nuovo esercizio.
   In alcune condizioni l'apertura, selezione o conferma di un nuovo esercizio
   puo causare blocchi/freeze.
   Possibili cause:
   - troppe renderizzazioni consecutive del catalogo;
   - immagini animate caricate in massa;
   - traduzione dei nomi esercizi ripetuta su molti record;
   - renderWorkout chiamato subito dopo aggiornamento ordine/esercizi;
   - interazione tra exercise-catalog.js, workout-editor.js,
     universal-exercise-editor.js e dynamic-workout-days.js.
   Prima di introdurre nuove funzioni, stabilizzare questo flusso.
   Verificare in particolare:
   - apertura catalogo;
   - ricerca nel catalogo;
   - selezione esercizio;
   - conferma aggiunta esercizio;
   - ritorno alla scheda;
   - persistenza dopo reload.

9. Problema aperto - Traduzioni e performance catalogo.
   La traduzione automatica dei nomi esercizi puo impattare le performance se
   eseguita molte volte durante filtro, ricerca e ordinamento.
   Verificare che la cache delle traduzioni sia presente anche nella stabile,
   non solo nella beta.
   Verificare che la ricerca usi debounce per evitare ricalcoli a ogni singolo
   input.
   Evitare di ritradurre l'intero catalogo quando cambia solo la selezione
   visiva di un esercizio.

===============================================================================
NOTE OPERATIVE PER FUTURE MODIFICHE
===============================================================================

- Non lavorare sulla cartella locale vecchia come fonte unica.
- Prima di modificare codice, leggere il repository remoto aggiornato.
- Tenere separate stabile e beta.
- Aggiornare sempre:
  - versione;
  - changelog;
  - service worker/cache;
  - README se la modifica riguarda utenti finali;
  - questo diario.
- Per modifiche delicate, implementare prima in beta.
- Evitare refactor grandi se non necessari.
- Preferire funzioni semplici, testabili e reversibili.
- Non introdurre backend finche backup/export/storico locale bastano.

Regola anti-frammentazione:

- Evitare di aggiungere nuovi file JavaScript per ogni micro-correzione.
- Prima valutare se la modifica puo essere integrata nel file gia responsabile
  della funzione.
- Nuovi file separati vanno creati solo se introducono un modulo realmente
  distinto.
- Ogni nuovo script aggiunto a index.html deve avere una motivazione chiara nel
  diario.
- Evitare refactor grandi non necessari.
- Preferire correzioni piccole, isolate e testabili.

Regola di verifica prima di dichiarare stabile:

Prima di dichiarare una funzione stabile, verificare almeno:

- test su browser desktop;
- test su iPhone reale quando la funzione riguarda uso mobile;
- nessun errore applicativo in console;
- comportamento corretto dopo reload;
- dati salvati correttamente in localStorage;
- eventuale export/share/download funzionante;
- cache aggiornata se la modifica riguarda file statici versionati.
